# erp/payment 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态、规则要点、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目：付款认领、资金事实与核销在协议 05，审批与职责分离在协议 09（运行时的流程内核是线协议第 17 章），对外命令与对账在协议 10（首批没有适配器），关账的封存在协议 06（首批不做），单号与金额在协议 14，期初在协议 16，数据范围在安全 07；决定 D47。端到端的位置见装配项目的业务流程“订单到收款”“采购到付款”的第 6 步。首批范围是装配项目阶段计划 C3 的 P0 定的（AI 定，待复核）。

## 边界

资金的结果：公司银行账户、收款登记、付款申请与执行、资金调拨与科目收付、银行对账。首批只有线下登记：钱在银行里由人办，本组件记下受理、批准、执行与到账，并把资金事实交给财务核销。

| 不在这里 | 归谁 |
| --- | --- |
| 应收应付未清项、核销、付款认领的额度、到期未清项 | `erp/finance`（本组件付款前向它认领；按它定义的资金事实与会计事实契约发布，D47） |
| 科目与凭证 | `erp/finance`（来源不写科目：资金事实带规则键，财务按映射出分录） |
| 账单 | `erp/billing` |
| 对银行或支付渠道发出指令、接收回调 | 支付与银行适配器（`integration/payment-*`、`integration/bank-*`，不在当前重建；协议 10） |
| 审批的统一待办 | `infra/workflow`：收本组件发布的任务投影，动作直达本组件（本组件是付款申请与调拨收付两种审批的流程管理方，用 SDK 的流程内核） |
| 员工、任职与账号关联 | `mdm/employee`（流程内核投影它：岗位上是谁、账号归哪个人） |
| 伙伴、法人、币种与汇率 | `mdm/partner`、`mdm/org`、`mdm/currency` |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 公司银行账户 | 法人在银行开的账户：开户行、账号、币种；收付款都记在一个账户上 | `bank_account`；状态 `active`、`inactive` |
| 收款单 | 线下到账的登记：付款方、账户、金额、到账日期、银行流水号；登记即到账 | `receipt`；状态 `received`、`reversed` |
| 付款申请 | 要付给一个伙伴的钱：针对财务的一个或几个未清项（应付，退款时是客户的贷方余额），经审批后由人在银行办理，再登记执行 | `payment_request`、`payment_request_line`；种类 `payment`、`refund` |
| 付款认领 | 付款申请对财务一个未清项的认领（协议 05 的认领模式，属主是财务）；认领身份由本组件生成 | `payment_request_line.claim_id` |
| 付款建议 | 按到期日列出财务的到期未清项（可用余额大于零），勾选生成付款申请 | — （查询财务的 `DueItems`） |
| 付款政策 | 按法人：付款申请与调拨收付的审批人（`mdm/org` 的岗位或指定个人）；付款总要人审批，没有“不要审批” | `payment_policy` |
| 审批实例与审批任务 | 一次提交的审批（流程内核的实例与任务，线协议第 17 章）；付款申请与调拨收付各一种流程 | SDK 的表 `be_flow_*`；任务类型 `erp.payment.request.approval`、`erp.payment.entry.approval` |
| 放行 | 批准之后、人去银行办理之前：向财务确认认领（确认后不会到期），申请可以去付了；同时核对审批仍覆盖申请（线协议 P17.7 的放行核对） | 状态 `ready` |
| 执行 | 线下付出之后的登记：实付金额（可少于申请，可逐行给）、付款日期、银行流水号 | `payment_request` 的 `paid_*` 字段 |
| 退回 | 已登记执行的钱没有付成（银行退回，或登记错了）：冲正，财务冲回认领、未清项重开 | 状态 `returned` |
| 资金调拨、科目收付 | 公司账户之间的调拨（转出与到账两步，之间是在途资金）；银行手续费、利息：不针对伙伴的未清项，经审批后直接过账 | `bank_entry`；种类 `transfer`、`charge`、`interest` |
| 资金事实 | 到账、付款、退款与它们的冲正，带认领清单；按财务的 `fund_fact.v1` 发布 | 事件类型 `erp.payment.fund_fact.v1` |
| 会计事实 | 资金调拨与科目收付；按财务的 `accounting_fact.v1` 发布 | 事件类型 `erp.payment.accounting_fact.v1` |
| 对账单行、对账 | 银行对账单上的一行；与已登记的收付款、调拨与收付匹配；匹配不上的是差错 | `statement_line`；状态 `unmatched`、`matched`、`resolved` |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `bank_account` | 法人、开户行、账号（受限字段）、币种、名称、状态 | 不删除，停用 |
| `receipt` | 内部号、法人、账户、付款方（可空）、金额与币种、到账日期、银行流水号、订单参考、状态、登记人、冲正原因 | 不删除；冲正是新状态 |
| `payment_policy` | 按法人：审批人（岗位身份 `approver_position_id` 或个人 `approver_principal`，至多一个）、版本 | 版本化，不删除 |
| `payment_request`、`payment_request_line` | 申请：内部号、法人、法人的时区（审批按法人当天判断谁在岗）、种类、收款方、账户、币种、金额、用途、参考号、部门、状态、申请人、审批人、执行人、实付金额、付款日期、银行流水号、驳回或退回原因；行：财务的未清项、本次金额、认领身份、认领期限、实付到这一行的金额 | 不删除 |
| `bank_entry` | 内部号、法人、法人的时区、种类、账户（调拨另有转入账户）、金额、日期（调拨另有到账日期）、说明、状态、制单人、审批人、提交时取的汇率快照（批准即过账在决定的事务里，不能再取证）、来源的对账单行 | 不删除 |
| 审批实例、任务、候选、决定与员工投影（SDK 的表 `be_flow_*`，投影 `be.flow.employee`） | 流程内核的状态；本组件不直接写 | 不删除 |
| `statement_line` | 账户、日期、金额（收为正、付为负）、银行流水号、摘要、状态、匹配到的单据、差错的处理说明 | 不删除 |
| `payment_fact` | 本组件发布的增量事实（资金事实、会计事实），按身份读回 | 随账务 |

以后还有：外部指令与结果（适配器）、封存记录（关账）。

| 规则 | 内容 |
| --- | --- |
| PR01 | 申请：法人、种类（付款或退款）、收款方（活跃的伙伴）、公司账户（同一法人、启用）、币种（= 账户的币种）、用途与参考号、可选部门（法人的活跃部门）；每行一个财务的未清项与本次金额（大于零）；同一未清项在一张申请里只出现一次；金额 = 各行之和；内部号 `PR`（按法人与年，允许缺号）。只在草稿时按版本整份修改（行整体替换）。草稿时不向财务核对：未清项是不是收款方的、可用余额够不够，都在提交时核对（PR02）。付款建议列出的是财务答的到期未清项（`DueItems` 的到期日可以给到将来，未到期的也能付）。没装财务时：行不带未清项，只写金额 |
| PR02 | 提交：提交人就是这张申请的**申请人**（职责分离按他算）。先核对每行的未清项是收款方的、可以付的：向财务查到期未清项（`DueItems`：法人、收款方、种类——付款查应付，退款查客户贷方余额——到期日不限），每行的未清项都要在里面、币种是申请的币种，否则答 `OPEN_ITEM_NOT_PAYABLE`、什么也不认领（财务的认领不知道收款方是谁，这一步不能省；应收不会在里面）。然后每行生成一个认领身份，在事务外逐行向财务认领（`ClaimService.Claim`，按认领身份幂等）；全部成功才在一个事务里写下认领与各自的期限、变成 `submitted`；有一行被拒（可用余额不够，未清项不能认领），已成功的那些行同时释放，申请留在草稿，答财务的原因。没装财务时直接 `submitted` |
| PR03 | 审批经流程内核：提交（PR02 认领都成功之后的那个事务）启动审批实例（关键修订号固定为 1：提交之后不能修改；依据摘要是种类、收款方、账户、币种、金额与每行的未清项与本次金额），任务按法人的付款政策分配（岗位在法人当天的持有人，或指定个人）；政策没配审批人时提交答 `NO_APPROVER_CONFIGURED`，在向财务认领之前判断，什么也不认领。批准与驳回是对任务的决定（线协议 P17.10 的检查：候选、不是申请人这个人——装了员工组件时按人，没装时只能比较账号、风险写进 `BRICKKIT.md`——、操作 `erp.payment.request.approve`、岗位此刻仍在岗），经标准路由或原来的 `approve`、`reject` 路由（原路由先按本组件的规则答：驳回要原因、状态表的忽略与拒绝，线协议 P17.14）；驳回必须附意见：实例退回，申请回到草稿，意见是原因，认领在同一事务里排一个释放的工作项（决定的事务里不调用财务），再提交时用新的认领身份。已批准的申请被驳回（还没放行）是本组件的规则，不是任务的决定：先释放认领，已批准的实例被取代（`superseded`），回到草稿 |
| PR04 | 放行（批准之后、人去银行办理之前：协议 05 要求不可撤回的动作之前确认）：放行人不是申请人这个人（同 PR03，按人；没装员工组件时比较账号）；先做放行核对（已批准的实例覆盖申请此刻的内容，否则 `NOT_RELEASED`）；在事务外逐行向财务确认认领（`Confirm`，幂等；确认后财务不再让它到期，只能由本组件释放或由财务按付款事实正式化）；有一行确认不了（认领已到期或被释放）：这张申请已确认与待确认的认领全部释放、申请退回草稿（原因“付款认领已失效”，同 PR08），答 `CLAIM_LOST`，要重新提交——不留下已确认却付不出去的认领占着财务的未清项；全部确认后变成 `ready`。没装财务时直接 `ready` |
| PR05 | 执行（线下已付之后登记，在执行的事务里再做一次放行核对）：记下实付金额（大于零、不超过申请金额）、付款日期、银行流水号；实付可以逐行给（每行不超过本次金额，合计等于实付），不给就按行的顺序分；一个事务里发布资金事实（付款 `payment`、退款 `refund`；认领清单是“认领身份 → 这一行的实付”，实付为零的行不列），变成 `paid`。财务核销时按实付正式化认领，没付到的部分由财务同时释放（协议 05 的 CL07）；剩下没付的另开新的申请。线下一次付一笔，没有协议 05 里适配器那种“几张应付里部分成功”的逐条结果 |
| PR06 | 退回（银行把已付的整笔钱退了回来，或执行登记错了、钱其实没付出去）：写明原因，一个事务里发布冲正的资金事实（`reverses_fact_id` 指向付款事实，规则键、金额与汇率快照同原事实，业务日期是法人当地的今天），变成 `returned`；财务冲回认领的正式化、未清项重开（CL09），可以再开申请去付。部分退回不在首批（财务的部分冲正也要人处理，ST05） |
| PR07 | 取消：已付的不能取消（走 PR06）；`submitted`、`approved`、`ready` 的同时向财务释放认领（`Release`，幂等；已确认的认领由使用方释放，CL06）；待审批的实例撤回（`withdrawn`），已批准的被取代；取消审计 |
| PR08 | 认领的续期：`submitted`、`approved` 的申请，每条认领在期限前由后台工作续期（`Renew`；在期限前一个小时排工作项，期限短于两小时时在剩余时间的中点，续期后按新期限再排；财务不可达时工作项重试）；续期被拒（认领已到期，或已经确认），工作项把申请退回草稿（原因写“付款认领已失效”，申请上看得到）、释放它的全部认领（被拒的那条也释放：已确认的仍占着财务的未清项；已到期的释放在财务那边什么也不做），要重新提交；待审批的实例撤回，已批准的被取代。`ready` 的认领已确认，不再续期 |

拒绝的原因：状态不允许 `STATE_CONFLICT`；未清项不是收款方可付的 `OPEN_ITEM_NOT_PAYABLE`；放行人是申请人这个人 `APPROVER_IS_SUBMITTER`；审批的决定被拒按线协议的原因（申请人这个人 `SELF_APPROVAL`、不是候选 `NOT_ASSIGNEE` 等，P17.10）；政策没配审批人 `NO_APPROVER_CONFIGURED`；放行核对不过 `NOT_RELEASED`；认领被财务拒绝时照财务的原因（`CLAIM_EXCEEDS_AVAILABLE`、`CLAIM_CONFLICT`、`CLAIM_STATE`）；放行时认领已失效 `CLAIM_LOST`（申请已退回草稿）；财务不可达 `DEPENDENCY_UNAVAILABLE`（什么也没改，可以重试）；版本不对 `VERSION_CONFLICT`。

| BE01 | 种类：调拨（转出与转入两个账户：同一法人、同一币种、都启用、不同）、手续费、利息（一个账户）；金额大于零；日期；说明；可以从对账单行生成（BR04）；内部号 `BE`（按法人与年，允许缺号）；只在草稿时按版本修改 |
| BE02 | 审批经流程内核（同 PR03）：提交时取汇率快照（按单据日期，事务之前取证）、启动审批实例（关键修订号固定为 1，依据摘要是种类、账户、转入账户、币种、金额、日期），没配审批人答 `NO_APPROVER_CONFIGURED`；批准与驳回是对任务的决定，批准人不是制单人这个人；驳回必须附意见、回到草稿；取消待审批的撤回审批。批准即过账（在决定的事务里，用提交时的汇率快照），一个事务里发布会计事实（共享契约的分析维度只有部门与项目，不带账户；财务按法人把 `bank` 角色映射到科目）：手续费 `bank_charge`（角色 `expense`、`bank`）、利息 `bank_interest`（`bank`、`income`），变成 `posted`；调拨发布转出的一条 `fund_transfer_out`（`in_transit` 借、`bank` 贷），变成 `in_transit`（协议 05：调拨是成对的两条事实，带同一调拨身份，在途期间记入在途资金） |
| BE03 | 到账（钱进了转入账户）：写明到账日期（不早于转出日期），一个事务里发布转入的一条 `fund_transfer_in`（`bank` 借、`in_transit` 贷），变成 `posted`。两条事实的来源都是这张调拨单（同一单据身份），财务的在途科目在到账之后归零 |
| BE04 | 过账（或转出）之后不取消；调拨转错了另做一张相反的调拨；手续费、利息的更正见未决问题 |

### 对账单行

| 命令 | `unmatched` | `matched` | `resolved` |
| --- | --- | --- | --- |
| 匹配 `match` | 指定的单据可以匹配时 → `matched` BR02 | 拒绝 BR02 | 拒绝 BR02 |
| 取消匹配 `unmatch` | 拒绝 BR02 | → `unmatched` BR02 | 拒绝 BR03 |
| 处理差错 `resolve` | 写明处理 → `resolved` BR03 | 拒绝 BR03 | 忽略 BR03 |
| 重新打开 `reopen` | 拒绝 BR03 | 拒绝 BR03 | → `unmatched` BR03 |
| 生成科目收付 `create_entry` | 允许：生成草稿 BR04 | 拒绝 BR04 | 拒绝 BR04 |

| 规则 | 内容 |
| --- | --- |
| BR01 | 对账单行按账户成批登记（用户面提交 JSON 行：日期、金额，收为正、付为负、银行流水号（可空）、摘要）；带流水号的行按“账户 + 流水号”去重（重复的跳过，答复里列出），没有流水号的不去重（每次登记都是新行，由人核对）。登记后自动匹配一次：BR02 的条件且银行流水号相同，唯一的一个才匹配；只有收款单与付款申请有流水号，所以自动匹配只对它们（调拨与收付手工匹配，或由 BR04 生成的那张过账时匹配回来源行）；本组件这边新登记收款或执行付款之后，也对同一账户还没匹配、流水号相同的行再试一次 |
| BR02 | 能匹配的单据：同一账户，金额相等、方向一致（收款与利息是收，付款、手续费是付；调拨的转出在转出账户是付、到账在转入账户是收，两条腿各匹配一行），状态是已到账、已付、已过账或已转出（已冲正、已退回的不匹配：银行的退票或退回是另一行，作为差错处理），还没有被别的行匹配（按单据，调拨按腿）。手工匹配可以不要求流水号相同，不满足这些条件答 `NOT_MATCHABLE`；取消匹配回到 `unmatched` |
| BR03 | 匹配不上的是差错：单边（银行有、本组件没有：补登记收款或付款、或从这一行生成科目收付，之后自动匹配；本组件有、银行没有：查明后在单据上处理，例如付款没付成就退回）、金额不符；差错按行写明处理说明后标为 `resolved`，可以重新打开 |
| BR04 | 从对账单行生成科目收付（协议 05 的 BL84）：付的行生成手续费、收的行生成利息的草稿（同一账户、金额、日期，说明取摘要，记下来源行），之后照 BE01–BE02 经审批；过账时自动匹配回这一行 |

一个账户的对账情况（查询）：某个日期范围内对账单行的合计、已匹配与未匹配的合计，本组件这一侧没有被匹配的单据。

## 规则要点

- **审批经流程内核**：任务按共享任务契约发布给统一待办，每个任务至多一个决定、重试只有一个决定；岗位上没人（或只有申请人自己）、员工投影不完整时任务暂停并告警，有 `erp.payment.flow.manage` 的人在 `GET /be/flow/tasks?state=paused` 看到；改政策只影响之后提交的单据。任务摘要只放单号、种类、金额与币种，不放账号与收款方。
- **每笔付给伙伴的钱都针对财务的一个未清项**（资金调拨与科目收付除外，它们直接过账）：提交审批前认领、放行时（人去银行办理之前）确认、财务按付款事实的实付正式化（协议 05）。没装财务时付款申请不针对未清项，只线下登记，人工核对（边界卡的缺件写法）。
- **受理、批准、执行、到账分别表达**（D47）：付款申请的提交与批准是受理与批准，执行是钱已付出的登记，到账是收款单；首批没有“通道已接收”，适配器来了以后加。
- **事实在业务事务里发布**：收款登记、付款执行、退回、冲正、调拨与收付的过账，都在同一个本地事务里写单据、写发件表与 `payment_fact`（不可遗漏的增量事实，协议 05 的共同规则：事实身份由本组件生成，按身份读回）。
- **事务里不调用别的组件**：认领、确认、释放、续期、订单核对、汇率快照都在事务之前（或之后的工作项里）；它们按身份幂等，重试安全。
- **外币**：账户的币种不是法人本位币时，事实带汇率快照（`mdm/currency` 的 `EffectiveRate`，按业务日期取，事务前取证）；本位币时汇率为空。付款申请的币种 = 账户 = 未清项的币种；财务首批的应付只有本位币（供应商票据与人工未清项都只收本位币），所以外币账户首批用于外币到账（财务分给同一币种的应收）与外币客户贷方余额的退款。
- **规则键**：到账 `receipt`、付款 `payment`、退款 `refund`；冲正沿用原事实的规则键；调拨 `fund_transfer_out`、`fund_transfer_in`，手续费 `bank_charge`，利息 `bank_interest`（财务的规则目录）。
- **过账日期**：等于业务日期；落在财务已关闭的月份时由财务顺延（PD01），首批本组件不封存。
- **账号是受限字段**（安全 09a）：读取键 `erp.payment.bank_account.number`，授予里列出这个字段的人才看全，其他人只看到后四位；审计里也只记后四位（SDK 只遮蔽审计变更的顶层字段，本组件把记录放在 `after` 里，所以审计前先遮蔽）。

## 整套恢复之后

存在性与版本：公司银行账户、收款单、付款申请、调拨与收付、对账单行（审计过的对象；对账单行每登记一行审计一条）。单号都是允许缺号的序列，没有要登记作废的号。

付款申请的认领以财务为准：`submitted`、`approved` 的申请续期照常（PR08），财务那边已经没有的认领续期被拒、申请退回草稿；`ready` 的申请由检查 `erp.payment.held_claims` 逐条向财务读认领，不是已确认的报出来，不自动改状态（钱可能已经付了），处置写在检查的答复里：钱还没付的取消后重新申请，已经付了的照实登记执行；`paid` 的申请事实已经发出，财务按身份去重。

## 验证故事

首批（线下登记）：

1. 付款申请提交时认领、财务的可用余额不够时整张不提交；批准、放行（确认认领）、执行后财务按实付核销，没付的部分回到可用余额。
2. 同一付款执行被重复提交，只付一次、只发一个事实。
3. 银行退回已付的款，财务的应付重开、可以再付。
4. 银行对账发现漏登记的到账：补登记后匹配。

边界卡的三个验证故事（付款超时后查询而不重发、对账发现漏收回调、恢复后不盲目再付款）要适配器，随第一个支付或银行适配器做。
