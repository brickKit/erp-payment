# erp/payment 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态、规则要点、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目：付款认领、资金事实与核销在协议 05，审批与职责分离在协议 09，对外命令与对账在协议 10（首批没有适配器），关账的封存在协议 06（首批不做），单号与金额在协议 14，期初在协议 16，数据范围在安全 07；决定 D47。端到端的位置见装配项目的业务流程“订单到收款”“采购到付款”的第 6 步。首批范围是装配项目阶段计划 C3 的 P0 定的（AI 定，待复核）。

## 边界

资金的结果：公司银行账户、收款登记、付款申请与执行、资金调拨与科目收付、银行对账。首批只有线下登记：钱在银行里由人办，本组件记下受理、批准、执行与到账，并把资金事实交给财务核销。

| 不在这里 | 归谁 |
| --- | --- |
| 应收应付未清项、核销、付款认领的额度、到期未清项 | `erp/finance`（本组件付款前向它认领；按它定义的资金事实与会计事实契约发布，D47） |
| 科目与凭证 | `erp/finance`（来源不写科目：资金事实带规则键，财务按映射出分录） |
| 账单 | `erp/billing` |
| 对银行或支付渠道发出指令、接收回调 | 支付与银行适配器（`integration/payment-*`、`integration/bank-*`，不在当前重建；协议 10） |
| 审批的统一待办 | `infra/workflow`（C7）；本版在本组件里审批 |
| 伙伴、法人、币种与汇率 | `mdm/partner`、`mdm/org`、`mdm/currency` |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 公司银行账户 | 法人在银行开的账户：开户行、账号、币种；收付款都记在一个账户上 | `bank_account`；状态 `active`、`inactive` |
| 收款单 | 线下到账的登记：付款方、账户、金额、到账日期、银行流水号；登记即到账 | `receipt`；状态 `received`、`reversed` |
| 付款申请 | 要付给一个伙伴的钱：针对财务的一个或几个未清项（应付，退款时是客户的贷方余额），经审批后由人在银行办理，再登记执行 | `payment_request`、`payment_request_line`；种类 `payment`、`refund` |
| 付款认领 | 付款申请对财务一个未清项的认领（协议 05 的认领模式，属主是财务）；认领身份由本组件生成 | `payment_request_line.claim_id` |
| 付款建议 | 按到期日列出财务的到期未清项（可用余额大于零），勾选生成付款申请 | — （查询财务的 `DueItems`） |
| 执行 | 线下付出之后的登记：实付金额（可少于申请）、付款日期、银行流水号 | `payment_request` 的 `paid_*` 字段 |
| 银行退回 | 已付的钱被银行退回：冲正，财务冲回认领、未清项重开 | 状态 `returned` |
| 资金调拨、科目收付 | 公司账户之间的调拨；银行手续费、利息：不针对伙伴的未清项，经审批后直接过账 | `bank_entry`；种类 `transfer`、`charge`、`interest` |
| 资金事实 | 到账、付款、退款与它们的冲正，带认领清单；按财务的 `fund_fact.v1` 发布 | 事件类型 `erp.payment.fund_fact.v1` |
| 会计事实 | 资金调拨与科目收付；按财务的 `accounting_fact.v1` 发布 | 事件类型 `erp.payment.accounting_fact.v1` |
| 对账单行、对账 | 银行对账单上的一行；与已登记的收付款、调拨与收付匹配；匹配不上的是差错 | `statement_line`；状态 `unmatched`、`matched`、`resolved` |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `bank_account` | 法人、开户行、账号（受限字段）、币种、名称、状态 | 不删除，停用 |
| `receipt` | 内部号、法人、账户、付款方（可空）、金额与币种、到账日期、银行流水号、订单参考、状态、登记人、冲正原因 | 不删除；冲正是新状态 |
| `payment_request`、`payment_request_line` | 申请：内部号、法人、种类、收款方、账户、币种、金额、用途、参考号、部门、状态、申请人、审批人、执行人、实付金额、付款日期、银行流水号、驳回或退回原因；行：财务的未清项、本次金额、认领身份、认领期限、实付到这一行的金额 | 不删除 |
| `bank_entry` | 内部号、法人、种类、账户（调拨另有转入账户）、金额、日期、说明、状态、制单人、审批人 | 不删除 |
| `statement_line` | 账户、日期、金额（收为正、付为负）、银行流水号、摘要、状态、匹配到的单据、差错的处理说明 | 不删除 |
| `payment_fact` | 本组件发布的增量事实（资金事实、会计事实），按身份读回 | 随账务 |

以后还有：外部指令与结果（适配器）、封存记录（关账）。

每张表在代码里是同一张表（`core.Table`），单元测试逐格比较。

### 付款申请

| 命令 | `draft` | `submitted` | `approved` | `paid` | `returned` | `cancelled` |
| --- | --- | --- | --- | --- | --- | --- |
| 修改 `edit` | 允许 PR01 | 拒绝 PR01 | 拒绝 PR01 | 拒绝 PR01 | 拒绝 PR01 | 拒绝 PR01 |
| 提交 `submit` | 认领全部成功时 → `submitted` PR02 | 忽略 PR02 | 忽略 PR02 | 拒绝 PR02 | 拒绝 PR02 | 拒绝 PR02 |
| 批准 `approve` | 拒绝 PR03 | 批准人不是申请人时 → `approved` PR03 | 忽略 PR03 | 忽略 PR03 | 拒绝 PR03 | 拒绝 PR03 |
| 驳回 `reject` | 拒绝 PR03 | 写明原因 → `draft` PR03 | 写明原因 → `draft` PR03 | 拒绝 PR03 | 拒绝 PR03 | 拒绝 PR03 |
| 执行 `execute` | 拒绝 PR04 | 拒绝 PR04 | 认领都已确认时 → `paid` PR04 | 忽略 PR04 | 拒绝 PR04 | 拒绝 PR04 |
| 退回 `return` | 拒绝 PR05 | 拒绝 PR05 | 拒绝 PR05 | 写明原因 → `returned` PR05 | 忽略 PR05 | 拒绝 PR05 |
| 取消 `cancel` | → `cancelled` PR06 | → `cancelled` PR06 | → `cancelled` PR06 | 拒绝 PR06 | 拒绝 PR06 | 忽略 PR06 |

| 规则 | 内容 |
| --- | --- |
| PR01 | 申请：法人、种类（付款或退款）、收款方（活跃的伙伴）、公司账户（同一法人、启用）、币种（= 账户的币种）、用途与参考号、可选部门（法人的活跃部门）；每行一个财务的未清项与本次金额（大于零、不超过登记时财务答的可用余额），未清项的伙伴是收款方、币种是申请的币种、种类与申请相符（付款对应付，退款对客户的贷方余额）；同一未清项在一张申请里只出现一次；金额 = 各行之和；内部号 `PR`（按法人与年，允许缺号）。只在草稿时按版本整份修改（行整体替换）。没装财务时：行不带未清项，只写金额 |
| PR02 | 提交：每行生成一个认领身份，在事务外逐行向财务认领（`ClaimService.Claim`，按认领身份幂等）；全部成功才在一个事务里写下认领与各自的期限、变成 `submitted`；有一行被拒（可用余额不够、未清项不能认领），已成功的那些行同时释放，申请留在草稿，答财务的原因。没装财务时直接 `submitted` |
| PR03 | 审批：批准人不是申请人（按账号；有员工组件与 C7 的业务确认 profile 之后按人，协议 09 的 D10），按版本；驳回写明原因、释放认领、回到草稿（再提交时用新的认领身份）；批准与驳回都审计 |
| PR04 | 执行（线下已付之后登记）：执行人不是申请人；先在事务外逐行向财务确认认领（`Confirm`，幂等；确认后财务不再让它到期）；有一行确认不了（认领已到期或被释放）就拒绝 `CLAIM_LOST`，申请保持 `approved`，要取消后重新申请。全部确认后一个事务里：记下实付金额（大于零、不超过申请金额）、付款日期、银行流水号，按行的顺序把实付分到各行（每行不超过本次金额），发布资金事实（付款 `payment`、退款 `refund`，认领清单是“认领身份 → 分到的金额”），变成 `paid`。财务核销时按实付正式化认领，没付到的部分由财务同时释放（协议 05 的 CL07） |
| PR05 | 银行退回已付的整笔钱：写明原因，一个事务里发布冲正的资金事实（`reverses_fact_id` 指向付款事实，金额相同），变成 `returned`；财务冲回认领的正式化，未清项重开（CL09）。部分退回不在首批（财务的部分冲正也要人处理，ST05） |
| PR06 | 取消：已付的不能取消（要退回走 PR05）；`submitted`、`approved` 的同时向财务释放认领（`Release`，幂等）；取消审计 |
| PR07 | 认领的续期：`submitted`、`approved` 的申请，每条认领在期限前由后台工作续期（`Renew`；在期限前一个小时排工作项，续期后按新期限再排）；续期被拒（已到期）的记下，执行时答 `CLAIM_LOST`（PR04） |

拒绝的原因：状态不允许 `PAYMENT_STATE`；批准人或执行人是申请人 `APPROVER_IS_SUBMITTER`；认领被财务拒绝时照财务的原因（`CLAIM_EXCEEDS_AVAILABLE`、`CLAIM_CONFLICT`、`CLAIM_STATE`）；执行时认领已失效 `CLAIM_LOST`；版本不对 `VERSION_CONFLICT`。

一个账户的对账情况（查询）：某个日期范围内对账单行的合计、已匹配与未匹配的合计，本组件这一侧没有被匹配的单据。

## 规则要点

- **每笔付给伙伴的钱都针对财务的一个未清项**（资金调拨与科目收付除外，它们直接过账）：提交审批前认领、执行前确认、财务按实付正式化（协议 05）。没装财务时付款申请不针对未清项，只线下登记，人工核对（边界卡的缺件写法）。
- **受理、批准、执行、到账分别表达**（D47）：付款申请的提交与批准是受理与批准，执行是钱已付出的登记，到账是收款单；首批没有“通道已接收”，适配器来了以后加。
- **事实在业务事务里发布**：收款登记、付款执行、退回、冲正、调拨与收付的过账，都在同一个本地事务里写单据、写发件表与 `payment_fact`（不可遗漏的增量事实，协议 05 的共同规则：事实身份由本组件生成，按身份读回）。
- **事务里不调用别的组件**：认领、确认、释放、续期、订单核对、汇率快照都在事务之前（或之后的工作项里）；它们按身份幂等，重试安全。
- **外币**：账户的币种不是法人本位币时，事实带汇率快照（`mdm/currency` 的 `EffectiveRate`，按业务日期取，事务前取证）；本位币时汇率为空。
- **过账日期**：等于业务日期；落在财务已关闭的月份时由财务顺延（PD01），首批本组件不封存。
- **账号是受限字段**：列表与读取只显示后四位，有 `erp.payment.bank_account.read_number` 的人才看全（安全 07 的字段）。

## 事件

| 事件 | 流与类型 | 形状 |
| --- | --- | --- |
| 资金事实 | `erp.payment`，`erp.payment.fund_fact.v1` | 财务的共享契约 `fund_fact.v1`：到账（`receipt`，没有认领）、付款（`payment`）、退款（`refund`）带认领清单、冲正带被冲正的事实身份 |
| 会计事实 | `erp.payment`，`erp.payment.accounting_fact.v1` | 财务的共享契约 `accounting_fact.v1`：`fund_transfer`、`bank_charge`、`bank_interest` |
| 收款单 | `erp.payment`，`erp.receipt.changed.v1` | 完整状态 |
| 付款申请 | `erp.payment`，`erp.payment_request.changed.v1` | 完整状态（行与认领身份；不带账号） |

增量事实按 `fact_id` 去重；完整状态事件按版本覆盖。

## 验证故事

首批（线下登记）：

1. 付款申请提交时认领、财务的可用余额不够时整张不提交；批准、执行后财务按实付核销，没付的部分回到可用余额。
2. 同一付款执行被重复提交，只付一次、只发一个事实。
3. 银行退回已付的款，财务的应付重开、可以再付。
4. 银行对账发现漏登记的到账：补登记后匹配。

边界卡的三个验证故事（付款超时后查询而不重发、对账发现漏收回调、恢复后不盲目再付款）要适配器，随第一个支付或银行适配器做。
